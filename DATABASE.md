# Database and Supabase Guide

This guide describes the planned v1 database and a safe order for setting it up.
It is a design reference, not a claim that the schema or Supabase project has
already been created. The project is still scaffolded; see [PLAN.md](./PLAN.md)
and [ARCHITECTURE.md](./ARCHITECTURE.md).

## 1. What the database needs to do

The database supports a client-facing inquiry workflow and a private studio
review workflow:

1. A visitor submits a validated inquiry through the Next.js server.
2. The server stores it in Supabase PostgreSQL.
3. A client signs up or signs in with Supabase Auth and keeps a profile record.
4. Logged-in clients can review the exact project requests they submitted and see
   the latest studio status.
5. An authenticated, provisioned studio member lists and reads inquiries.
6. That member updates only the inquiry's follow-up status.

Continue to use Supabase Auth for credentials; the application stores only an
identity-linked `public.client_profiles` row for client-specific details and to
match requests to the signed-in user. The project stores its request records in
`public.inquiries`, with a nullable `client_id` that links each project request
back to the matching client profile when the user is logged in.

## 2. Request and trust boundaries

```text
Visitor
  └─ Next.js POST /api/inquiries
       ├─ Validate and normalize fields
       ├─ Check honeypot and shared rate limit
       └─ Server-only insert into public.inquiries

Studio member
  └─ Sign in with Supabase Auth
       └─ Next.js admin Route Handler
            ├─ Verify session and trusted studio-member authorization
            └─ Query using the member's Supabase session (RLS applies)
```

- RLS protects inquiry records even if a request bypasses the intended UI.
- Admin reads and updates must use the authenticated user's session, not a
  service-role client. Check authorization in the Route Handler too.
- The public endpoint's service-role client bypasses RLS. Keep it in a
  server-only module and expose only a narrow insert operation after validation
  and rate limiting. Never send its key to a browser or use the client for admin
  queries.
- Do not add a direct anonymous `INSERT` policy. A browser should not be able to
  bypass the validation, honeypot, and rate-limit checks.
- RLS does not replace input validation, authorization checks, rate limiting, or
  careful secret handling.

## 3. Initial schema

The initial migration is
[`supabase/migrations/20261107000000_create_inquiries.sql`](./supabase/migrations/20261107000000_create_inquiries.sql),
and the client-account extension is in
[`supabase/migrations/20261107010000_client_accounts_and_project_access.sql`](./supabase/migrations/20261107010000_client_accounts_and_project_access.sql).
Together they add `public.client_profiles` and a `public.inquiries.client_id`
link so a signed-in client can retrieve only their own project requests.

`public.client_profiles` stores:

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by the database. |
| `user_id` | `uuid` | Required; linked to `auth.users.id` with a unique constraint. |
| `full_name` | `text` | Required; user-entered display name. |
| `email` | `text` | Required; normalized email address, unique. |
| `company` | `text` | Optional; optional company name. |
| `created_at` | `timestamptz` | Required; defaults to the current time. |
| `updated_at` | `timestamptz` | Required; updates on profile changes. |

`public.inquiries` also includes a nullable `client_id` that references the
matching profile. The schema keeps the existing studio workflow while allowing a
client to read only rows whose `client_id` matches their own profile.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by the database. |
| `name` | `text` | Required; trim and limit to 120 characters. |
| `email` | `text` | Required; normalize and validate in the application, limit to 254 characters. |
| `company` | `text` | Optional; trim and limit to 120 characters. |
| `service` | `text` | Optional; one of `brand_identity`, `web_design`, `product_design`. |
| `project_brief` | `text` | Required; trim and limit to 5000 characters. |
| `budget_range` | `text` | Optional; `under_5k`, `5k_10k`, `10k_25k`, `25k_50k`, `50k_plus`, or `not_sure`. |
| `timeline` | `text` | Optional; trim and limit to 120 characters. |
| `status` | `text` | Required; `new`, `contacted`, `in_progress`, or `closed`; defaults to `new`. |
| `created_at` | `timestamptz` | Required; defaults to the current time. |
| `updated_at` | `timestamptz` | Required; defaults to the current time and changes on update. |

Use `NOT NULL`, `CHECK`, and default constraints as appropriate. The browser and
server should share allowed option values where practical, but the database
constraints remain the final guard against invalid stored status/service values.
The initial budget range values are an implementation choice for v1 and can be
revised before the form is built. Do not store the honeypot value or unnecessary
personal data. The rate limiter uses a hash of the platform-provided client IP
as its Redis identifier; configure the deployment proxy to set `x-real-ip`.

The only v1 status transition field is `status`. The API should reject arbitrary
fields, and the admin UI should offer only the four defined values.

## 4. Row Level Security design

Enable RLS on `public.inquiries`. Create policies with these properties:

| Operation | `anon` | `authenticated` |
| --- | --- | --- |
| `SELECT` | Denied | Allowed only to a provisioned studio member. |
| `INSERT` | Denied | Denied for direct table requests; public submission uses the narrowly scoped server-only insert client. |
| `UPDATE` | Denied | Allowed only to a provisioned studio member. |
| `DELETE` | Denied | Denied in v1; cleanup is a controlled operator/retention task. |

Use a server-controlled Supabase Auth `app_metadata` claim for the v1 access
level, for example `access_level: "studio_member"`. RLS policies can check
`auth.jwt() -> 'app_metadata' ->> 'access_level'`. Never authorize from
`user_metadata`, because users can edit it. The Next.js Route Handler must also
check the trusted claim; UI routing alone is not authorization.

For `UPDATE`, use both a `USING` condition (which rows the member can target) and
a `WITH CHECK` condition (which rows may exist after the update). Do not create
an authenticated delete policy or any anonymous read policy. Test each operation
as `anon`, an ordinary authenticated user, and a provisioned studio member.

RLS policies limit rows, not columns. Also review SQL privileges so
`authenticated` has `SELECT` and column-level `UPDATE` on `status` only, with no
table-level `INSERT` or `DELETE` permission. Revoke any broader default
privileges before granting the narrow set, and verify that the server-only
service-role client retains the minimum permission it needs for the public
insert. This prevents a direct database request from changing contact details
even when it comes from a studio member.

When setting up the first studio account, create/provision it privately and set
its trusted `app_metadata` through a trusted administrative mechanism, such as
the Supabase Dashboard. Never expose a service-role key to set claims from the
client. Refresh the session after changing claims so its JWT contains the
updated metadata.

## 5. Migration workflow

Keep all schema changes in versioned SQL under `supabase/migrations/`; do not
make untracked dashboard-only schema changes. The first migration should create
the table, constraints, `updated_at` behavior, enable RLS, and create the
policies. Give it a timestamped descriptive name, for example:

```text
supabase/migrations/20261107000000_create_inquiries.sql
```

Recommended workflow once the Supabase CLI and Docker are available:

1. Initialize the CLI if needed: `pnpm dlx supabase init`.
2. Start the local stack: `pnpm dlx supabase start`.
3. Create a migration: `pnpm dlx supabase migration new create_inquiries`.
4. Write the schema and RLS SQL in the generated migration.
5. Apply migrations locally and reset the local database from migrations:
   `pnpm dlx supabase db reset`.
6. Run SQL/RLS and API tests against the local project.
7. Link the intended hosted project and apply reviewed migrations:
   `pnpm dlx supabase link --project-ref <project-ref>` then
   `pnpm dlx supabase db push`.

Use the CLI's actual output to confirm each operation. Keep generated local
configuration and secrets out of version control; commit migration SQL, not
database dumps or credentials. Never test destructive database commands against
production.

## 6. Environment and project setup

Create a separate Supabase project for development/testing and production. Keep
the following in local `.env.local` and the deployment platform's secret
settings; `.env.example` contains placeholder values only:

| Variable | Use |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL used by the application. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Public/publishable key; RLS must make this safe to expose. |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only public-inquiry insert client; never prefix with `NEXT_PUBLIC_`. |
| `UPSTASH_REDIS_REST_URL` | Shared rate-limit store URL. |
| `UPSTASH_REDIS_REST_TOKEN` | Server-only rate-limit credential. |

Do not paste secrets into source files, commits, screenshots, issue trackers, or
logs. If a secret has been placed in a repository file or otherwise exposed,
rotate it in the provider before use and update the local/deployment secret
configuration. Use synthetic inquiry data in development and portfolio
screenshots.

## 7. Data retention and operations

Inquiries may contain personal data. Display a concise privacy notice explaining
the demo purpose and what is collected; do not invite sensitive information.
Delete demo submissions after 14 days, and honor earlier removal requests. Plan
and test the cleanup method before opening the demo publicly. Do not rely on
manual dashboard cleanup as the only production process.

Use database constraints and application validation together. Keep logs free of
names, email addresses, project briefs, session tokens, and secrets. If a
database write fails, return an error to the visitor; never show a success
confirmation for an unsaved inquiry.

## 8. Database verification checklist

- [ ] A clean local database can be created from committed migrations.
- [ ] Required fields, field lengths, allowed options, and statuses are enforced.
- [ ] Anonymous users cannot select, insert, update, or delete table rows directly.
- [ ] A signed-in user without the trusted studio-member claim cannot read or update rows.
- [ ] A provisioned studio member can list, read, and update status, but cannot delete rows.
- [ ] The public server endpoint can insert only after validation, honeypot, and rate-limit checks.
- [ ] Admin requests use the user's session so RLS applies; they never use the service-role client.
- [ ] Failed persistence does not produce a success response.
- [ ] The 14-day cleanup process and earlier deletion request path are tested before public release.

## 9. Suggested order of work

1. Create Supabase development and production projects; keep public signup
   disabled and provision the studio account privately.
2. Confirm inquiry option values and field-length limits.
3. Implement and review the first SQL migration, including RLS policies.
4. Apply it locally and verify permissions with distinct anonymous, ordinary
   authenticated, and studio-member sessions.
5. Add Supabase server/session clients while keeping the privileged insert
   client isolated.
6. Implement and test the public inquiry endpoint, then authenticated admin
   queries.
7. Add retention automation and deployment secrets before making the demo
   public.
